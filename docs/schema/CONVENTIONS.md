# Schéma physique v2 : conventions

Le schéma v2 (`docs/schema/schema_v2.sql`) est la traduction du schéma v1 de la spécification (`database/docs/BOID_MIRAH_schema.sql`, MySQL 8, noms français) vers PostgreSQL 16 + PostGIS 3.5 avec des identifiants en anglais (décisions D1, D2 et D3, voir `docs/decisions/`).

**Validation technique** : le fichier s'exécute tel quel sur une base PostGIS vide et crée 175 tables, 285 clés étrangères, 105 contraintes `CHECK`, 6 vues, 3 triggers et 4 partitions de `positions`. Les triggers d'audit et de verrouillage de la main courante, le routage des partitions, les contraintes d'énumération et une requête spatiale (point dans une zone, distance en kilomètres) ont été exercés sur des données d'essai.

**Validation métier** : acceptée par Gildas le 2026-10-27. Les noms se relisent dans `docs/GLOSSAIRE.md` (tables) et `docs/schema/GLOSSAIRE_COLONNES.md` (colonnes), et en particulier les traductions listées au point 3, qui restent modifiables tant que les migrations de la phase concernée ne sont pas écrites.

Les migrations Laravel sont écrites **phase par phase** à partir de ce fichier (voir `docs/PLAN_REFONTE.md`). Le fichier SQL n'est pas régénéré : en cas de changement, il est corrigé avec les deux glossaires.

## 1. Règles de nommage

| Objet | Règle | Exemples |
|---|---|---|
| Table | pluriel anglais, `snake_case` | `vessels`, `license_suspensions` |
| Table de liaison pure | deux singuliers, ordre alphabétique (convention Laravel) | `role_user`, `external_list_vessel`, `license_species` |
| Clé primaire | `id`, `bigint` identity | |
| Clé étrangère | `<entité>_id`, qualifié si ambigu | `vessel_id`, `flag_country_id`, `home_port_id`, `lead_user_id` |
| Auteur d'une action | `<participe>_by`, sans `_id` (comme `resolved_by` ou `handled_by` déjà en base) | `entered_by`, `decided_by`, `created_by` |
| Horodatage | suffixe `_at` (`timestamp`) | `occurred_at`, `received_at` |
| Date | suffixe `_on`, ou borne `_from` / `_to` / `_until` (`date`) | `expires_on`, `valid_from` |
| Booléen | `is_`, `has_`, `requires_` ou `includes_` selon le sens | `is_active`, `requires_vms` |
| Compteur | suffixe `_count` | `received_count` |
| Géométrie | `geometry` | `zones.geometry` |
| Mots réservés de PostgreSQL | évités | `order` devient `sort_order`, `check` devient `check_type`, `trigger` devient `trigger_event` |

Les noms français d'origine restent consultables : `COMMENT ON TABLE` / `COMMENT ON COLUMN` dans la base, et les deux glossaires.

## 2. Types

| MySQL (v1) | PostgreSQL (v2) |
|---|---|
| `BIGINT UNSIGNED AUTO_INCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` |
| `TINYINT(1)` | `boolean` |
| `ENUM(...)` | `varchar(40)` + contrainte `CHECK (col IN (...))`, valeurs en anglais `snake_case` |
| `JSON` | `jsonb` |
| `DATETIME`, `TIMESTAMP` | `timestamp(0)` (`timestamp(3)` pour le journal d'audit), en UTC |
| `DECIMAL(p,s)` | `numeric(p,s)` |
| `GEOMETRY`, `LINESTRING` | `geometry(Geometry, 4326)`, `geometry(LineString, 4326)` avec index GiST |
| Partition `RANGE` sur l'année et le mois | `PARTITION BY RANGE (emitted_at)` : partitions mensuelles et partition par défaut |
| `SIGNAL SQLSTATE` (triggers) | fonctions PL/pgSQL qui lèvent une exception |

Les valeurs d'énumération sont des **identifiants** : les libellés affichés passent par les fichiers de traduction (`lang/{en,fr}`), comme pour les énumérations actuelles.

## 4. Horodatage et suppression

- `created_at` et `updated_at` sont ajoutés à toute table dotée d'un `id`, sauf `positions` (volumineuse) et `audit_log` (qui a sa propre date). La spécification annonçait « `created_at` / `updated_at` partout » en en-tête sans les écrire dans les tables : cette interprétation est à confirmer.
- **Aucune suppression physique** des données métier (règle de la spécification). Pas de `deleted_at` sauf pour d'éventuels référentiels techniques.

## 5. Contraintes

- Toutes les clés étrangères sont déclarées à la fin du fichier, sous la forme `<table>_<colonne>_foreign`, ce qui supprime les problèmes d'ordre de création.
- Des clés étrangères ont été **ajoutées** sur `positions` (`vessel_id`, `zone_id`) : MySQL ne les permettait pas sur une table partitionnée, PostgreSQL oui.
- Les noms de contraintes et d'index sont tronqués à 63 caractères avec une empreinte.

## 6. Partitionnement

`positions` est partitionnée par mois sur `emitted_at`, avec une partition par défaut. Le fichier crée les partitions d'octobre à décembre 2026 ; la création des mois suivants sera une tâche planifiée du module VMS (phase 3b). La clé primaire est `(id, emitted_at)`.

## 7. Triggers

| Trigger | Effet |
|---|---|
| `audit_log_no_update_delete`, `audit_log_no_truncate` | le journal d'audit refuse toute modification, suppression ou vidage, y compris pour l'Admin |
| `logbook_entries_locked` | une journée de main courante verrouillée refuse la modification de ses lignes ; la correction se fait par une ligne rectificative |

## 8. Vues

`v_authorized_vessels` (RG01), `v_morning_board`, `v_expiring_licenses` (RG07), `v_vessel_timeline`, `v_repeat_offenses`, `v_seen_never_inspected`. Les vues `v_kpi_*` seront ajoutées module par module (phase 8).

## 9. Connecteurs : réconciliation avec la table actuelle

`data_sources` existe déjà (`key`, `name`, `kind`, `status`, `last_synced_at`) ; la spécification définit `etat_connecteur` (`code`, `mode`, `last_synced_at`, `indicator_status`, `last_error`, `is_stale`). Le schéma v2 reprend la spécification telle quelle. À la phase 7 :

| Actuel | Cible |
|---|---|
| `key` | `code` |
| `kind` (`api`, `database`, `file`) | `mode` (`api`, `import`, `scraping`, `direct_read`) |
| `status` (`operational`, `degraded`, `down`) | `indicator_status` (`green`, `orange`, `red`) |
| `name` | à conserver (absent de la spécification) |

`data_source_syncs` et `data_source_rejections` correspondent à `journal_synchro` et `rejet_import`. `data_source_errors` (suivi humain des erreurs) n'existe pas dans la spécification et est conservée. Les commentaires de connecteurs (`data_source_comments`) ont été repliés dans la table générique `comments`.

## 10. Écarts de la version 1 relevés pendant la traduction

À transmettre à l'auteur de la spécification.

1. `etiquette` (étiquettes génériques) est citée au §4 de la spécification mais absente du SQL.
2. `licence.statut` stocke `expiree` alors que l'expiration se déduit de la date d'expiration : risque d'incohérence (notre implémentation actuelle le calcule).
3. L'énumération `action_catalogue.verbe` contient une valeur accentuée (`clôturer`).
4. La colonne `navire_source.derniere_import` est probablement `derniere_importation` : le sens est conservé (`last_import_at`).
5. Le mot `saisie` désigne tantôt une saisie manuelle (origines : `manual_entry`), tantôt une saisie douanière (mesures conservatoires : `catch_seizure`, `gear_seizure`) : les deux sens sont distingués.
6. La clause `CHECK` de `permission` (un rôle ou un groupe, jamais les deux) est conservée sous la forme `(role_id IS NOT NULL) <> (permission_group_id IS NOT NULL)`.
7. Le seuil de silence VMS par défaut de `regle_alerte` est de 4 h : notre configuration actuelle est de 2 h (décision D9 : la spécification prévaut).

## 11. Écarts décidés à l'implémentation

Ces écarts par rapport au schéma v2 initial ont été décidés en écrivant les migrations ; le fichier SQL est tenu à jour avec eux.

| Table | Écart | Raison |
|---|---|---|
| `vessel_events` | `summary` (texte de 500 caractères) devient `summary_key` + `summary_params` (jsonb) | le résumé est traduit à l'affichage dans la langue de chaque lecteur (règle : aucun texte affiché en dur) |
| `activity_log` | sert de journal d'audit, rendu inaltérable par des triggers, en attendant la table `audit_log` | le paquet d'historisation écrit déjà dans cette table ; l'identité de l'agent IA et l'adresse IP sont dans `properties` |
| `users` | `password` devient nullable ; `type` est contraint à `human`, `ai_agent`, `system` | les comptes de type agent IA et système n'ont pas de mot de passe |
| `action_catalog` | pas de colonne `label` | le libellé d'une action est traduit à partir de son code (`permissions.<module>.<action>`) |
| `permission_groups` | `label` nullable, ajout de `is_system` | les cinq groupes de la spécification sont traduits à partir de leur code ; les groupes créés par l'administrateur portent leur nom |
| `roles` | `name` (au lieu de `code`), `description`, `parent_id` ; pas de colonne `label` ni `is_system` | le nom d'un rôle personnalisé tient lieu de libellé ; les rôles système se reconnaissent à l'énumération `Role` |
| `permission_grants` | utilisée pour les rôles **et** les groupes, comme le schéma, comme seule source des droits | le résolveur lit cette seule table |

| `comments` | ajout de `kind` (nullable, varchar(40)) | classer un commentaire (note, statut, action) ; les commentaires de connecteurs en ont besoin et la colonne reste générique, sa valeur est validée par le module propriétaire |
| `documents` | trigger `documents_frozen_guard` : un document figé refuse la modification et la suppression | la spécification annonce des PDF figés avec empreinte ; le verrou est porté par la base, comme celui de la main courante |
| `eez_declaration_checks` | `comment` contient un code court (`silent_beacon`, `no_valid_license`...) traduit à l'affichage, pas un texte | aucun texte affiché en dur ; la colonne reste libre pour un commentaire saisi à la main |
| `countries` | ajout de `iso2_code` (char(2), unique, nullable) | les pavillons de l'application existante sont des codes ISO à deux lettres ; la table garde aussi le code à trois lettres du schéma |
| `ports` | conserve `locality`, `latitude`, `longitude` (absents du schéma) ; `name` reste unique | l'application les utilise (comptage par zone, cartes, saisie des mouvements) |
| `species` | conserve les colonnes `fao_code`, `name`, `scientific_name` (schéma : `code_fao`, `label`) ; `fao_code` passe à 10 caractères, `scientific_name` devient facultatif | éviter de casser les captures, la page des espèces et leurs tests ; le code FAO reste l'identifiant unique |
| `vessels` | conserve `registration_number`, `imo_number`, `call_sign` (copie du numéro actif, synchronisée vers `vessel_identifiers`), `type` (énumération historique, devenue facultative), `category` (`fishing`, `patrol`), `status` ; `length_meters` devient `length_m` ; ajout de `fleet_segment` (valeurs de la catégorie du schéma : vedette, industriel, semi-industriel, artisanal, étranger autorisé, connu non autorisé) ; `deleted_at` est conservé ; `flag` et `owner` sont supprimés au profit de `flag_country_id` et de `vessel_actors` | les autres modules lisent ces colonnes ; la catégorie du schéma ne peut pas porter le même nom que la catégorie historique |
| `vessel_identifiers` | index unique partiel sur `(type, value)` pour les lignes actives (`valid_to IS NULL`) | la contrainte `UNIQUE (type, value, valid_from)` du schéma n'interdit pas deux identifiants actifs identiques (`valid_from` nul) ; l'unicité est la règle RG02 |
